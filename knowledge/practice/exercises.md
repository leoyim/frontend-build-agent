## 项目 1 · 手写迷你打包器

**对应**：第 2 章 §2.1

**目的**：验证你对依赖图的理解**不是背来的**。

**规模上限**：≤ 100 行。

### 任务

用 Node.js 从零实现一个极简打包器，输入两个互相 `import` 的文件，输出一个可在浏览器运行的 JS 文件。

```text
src/
  index.js    →  import { add } from './add.js'; console.log(add(1, 2));
  add.js      →  export function add(a, b) { return a + b; }
```

**必须实现的三步**（对应 §2.1 的 resolve / load+transform / parse）：

| 步骤 | 要做的 |
|---|---|
| ① resolve | 把 `'./add.js'` 从 `src/index.js` 出发补成绝对路径 |
| ② load + transform | 读文件内容，把 ESM 语法转成一个可注册的模块函数 |
| ③ parse | 找出这个文件里的 import，**入队**（不是递归立刻处理 —— 用队列才能看出"图"的形状） |

**建议的输出结构**：

```js
const modules = {
  'src/index.js': function (require, module, exports) { /* 转换后的代码 */ },
  'src/add.js':   function (require, module, exports) { /* 转换后的代码 */ },
};
// 自己实现一个极简 require，按绝对路径查表
```

### 过关判据（两条，都要满足）

1. **跑通「两个文件互相 import」** —— 在浏览器里能输出 `3`。
2. **能解释「共享模块为何只处理一次」** —— 造一个场景：`index.js` 和 `b.js` 都 import `shared.js`，然后回答：
   - 你的打包器处理了 `shared.js` 几次？
   - 运行时它执行了几次？
   - 这两个数**为什么应该相等**？

> **第 2 条判据直指 §2.1 的「图 ≠ 树」** —— 你必须自己处理去重（比如用一个 `Set` 记录已处理的绝对路径），才能真正体会"为什么去重发生在内存层，而不是产物层"。

### 完成后再想一个问题

**你的打包器会把 `shared.js` 在产物里输出几份？**（答案：1 份，因为你的 `modules` 表用绝对路径做 key。）
**那如果 `index.js` 和 `b.js` 分别打包成两个产物文件呢？**（这时才会有重复 —— 这就是 §2.2 讲的，产物层去重是 `splitChunks` 的事。）

## 项目 2 · 零插件 Vite 项目

**对应**：第 3 章 §3.3

**目的**：把"Vite 的默认值覆盖了语言层"从**陈述**变成**体感**。

**规模**：1 小时。

### 任务

1. 建一个 Vite + TypeScript 项目，**不装任何额外插件**。
2. 依次做四件事，每做一件**确认它不需要配置**：
   - 写一个 `.ts` 文件，用上类型标注和 interface
   - 写一个 `.tsx`（或 `.vue`）文件
   - `import './style.css'`，用上类名
   - `import logo from './logo.svg'`，把它当字符串用

3. **反直觉动作：把 `vite.config.ts` 删掉，看项目还能不能跑。**

### 过关判据

1. **每一行配置能说出「为什么存在」** —— 如果 `vite.config.ts` 里有一行你解释不了，删掉它试试。
2. **删掉配置后项目仍能跑** —— 说明那些配置本来就不需要。

> **这个判据的威力**：它会暴露"抄来的配置"。很多人 `vite.config.ts` 里塞了 `resolve.alias`、`server.proxy`、`build.sourcemap` —— 但问不出为什么要有这些，也不知道删掉会怎样。

### 追问

**删掉配置后 `npm run build` 还能跑吗？** 如果不能，是哪一行配置在起什么作用？

## 项目 3 · hash 预测游戏 ⭐

**对应**：第 2 章 §2.2、第 7 章 §7.2 台阶 3

**这本书最推荐的一项练习。** 它是"从使用者变成工程化"的转折点。

**规模**：半天。

### 准备工作

1. 建一个**三页面**的 Vite 项目（三个路由 / 三个 HTML 入口均可）。
2. 装 `rollup-plugin-visualizer`，先看一眼产物构成。
3. 配置里确保有：`[contenthash]`、`manualChunks`（或 Vite 的默认分组）、稳定的 `moduleIds`。

### 玩法

**每一轮：先写预测，再动手，最后对照。**

| 轮次 | 改动 | 动手前先写下来 |
|---|---|---|
| 1 | 改一个页面的业务代码 | 哪些产物的文件名会变？ |
| 2 | 升一个依赖的小版本 | 哪些会变？ |
| 3 | 只改一个 CSS 值 | 哪些会变？ |
| 4 | **只改一行注释** | **应该什么都不变吗？** |
| 5 | 新增一个页面入口 | 哪些会变？ |

### 过关判据

**连续 5 次预测正确。**

### 预测错了怎么办

**不要跳过，要追根因。** 每个错误都对应某一块理解不到位：

| 预测错误的表现 | 说明哪块没通 |
|---|---|
| 只改注释，hash 却变了 | **缓存三件套没配齐** —— 运行时胶水污染了 chunk（§2.2） |
| 改了业务代码，vendor 也变了 | `moduleIds` 不是 `deterministic`，模块 ID 重排 |
| 改了 A 页面，B 页面也变了 | 抽包策略把两者绑在同一个 chunk 里 |
| 新增页面入口，别的都没变 | 正常 —— 但要能解释**为什么**没变 |

### 加分项

用 `rollup-plugin-visualizer` 打开 vendor chunk 的模块排行，**指出体积前 3 的模块，并说出它们为什么在同一个 chunk 里**。

## 项目 4 · 构建基准测量

**对应**：第 5 章 §5.6

**规模**：半天。

完整实验设计见 `experiments.md`。

### 任务

按六步法跑一遍基准测量，产出一段**结论文字**。

### 过关判据

**结论的每一句都带前提。**

**不合格**：

> "升级到 Vite 8 后构建提速约 6 倍。"

**合格**：

> "在 ___ 机器（___ 核 / ___ G）上，对一个约 ___ 行代码、___ 个依赖、___ 个插件的项目，清空 `node_modules/.cache`、`node_modules/.vite` 与浏览器缓存后，**生产构建**耗时从 ___ 秒降到 ___ 秒（各跑 5 次取中位数）。"

### 一个必须做的对照

**同一台机器上，测一次"清缓存"和一次"不清缓存"。** 观察差异 —— 这能让你对"90s → 12s 可能是缓存差异"这类说法有直接体感。

## 项目 5 · 迁移评估一页纸

**对应**：第 7 章 §7.6

**规模**：半天。

### 任务

挑一个你熟悉的存量项目（真实的或假想的），按 §7.6 的模板写一页纸评估报告。

### 过关判据

**报告必须包含「回退路径」那一段。**

没有回退路径的评估报告是**假报告** —— 它假设迁移一定成功。

### 五段结构

| 段落 | 关键要求 |
|---|---|
| ① 现状与痛点 | **必须有具体数字**（不是"构建很慢"，是"生产构建 4 分 20 秒，每次 CI 阻塞发布"） |
| ② 依赖清单核对 | 逐条列出 loader / plugin，标出是否支持、替代方案 |
| ③ 硬阻塞 | 浏览器兼容要求；是否用了不支持的能力 |
| ④ 产物回归方案 | 怎么证明迁移后产物没变坏 |
| ⑤ **回退路径** | **触发条件 / 回退动作 / 回退耗时** |

## 附：课程中未作答的习题

以下题目在课程中提出但**未作答**，相关知识点未经复述验证。列此备查 —— 它们恰好构成一套不错的小练习。

| 出处 | 题目 | 涉及知识点 |
|---|---|---|
| 模块 3 §2 | esbuild 和 SWC 都不做类型检查 —— 那你在 Vite 项目里写的类型错误，是怎么被发现的？`vite build` 会不会因此失败？ | 转译器职责边界（§4.2） |
| 模块 3 §2 | 有个用了 5 个 Babel 插件的老项目，想把 Babel 换成 SWC，动手之前你会先评估什么？ | 插件体系不通用（§4.2） |
| 模块 4 §2 | 五个动手项目里哪个最容易被自己"糊过去"？为什么？你会加什么额外判据堵住？ | 判据设计（§7.3） |
| 模块 4 §2 | 判断"升级到 Vite 8 后构建提速约 6 倍"是否符合"每句都带前提"的判据；不符合就改写 | 六步测量法（§5.6） |
| 模块 4 §3 | 给团队引入 Rolldown，先读三种文档读法里的哪一类？为什么它优先？ | 迁移指南性价比最高（§7.4） |
| 模块 4 §3 | `vite build` 报错且网上搜不到，按三个源码切入点第一步走哪个？具体"敲什么"？ | 搜报错字符串 → 顺调用栈读那一条路径（§7.4） |

**参考方向**（不是标准答案，请先自己想）：

- 第 1 题：类型检查由**另一条流水线**负责（`tsc --noEmit` / `vue-tsc --noEmit`），转译器只剥离标注。`vite build` **默认不会**因类型错误失败。
- 第 2 题：先列 Babel 插件清单，逐个找 SWC 等价物；找不到的评估改写成本或限制作用范围。核心机制是**插件体系不同**（JS vs Rust/WASM）。
- 第 3 题：最容易糊过去的是**台阶 2（零插件 Vite 项目）** —— "能跑"不等于"知道每行配置为什么在"。堵法：加"删掉配置还能跑"这个判据。
- 第 4 题：不符合。缺机器、代码规模、清了哪些缓存、跑了几次、中位数。
- 第 5 题：**迁移指南**。因为它是官方承认的差异清单，等于免费的对照表；Lint/API 页都拿不到"哪里会变"。
- 第 6 题：**先搜报错字符串**（在依赖源码里搜），再顺调用栈往回读那一条路径。而不是从 `index.js` 开始读起。
